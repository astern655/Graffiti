# 제약 조건 기반 데모-우선 웹 도구 MVP 패턴

## 언제

- 2-3일 타임박스 제약이 있는 프로젝트
- "설치 없음, 서버 없음, 학습 곡선 없음" 요구사항
- 브라우저에서 단일 HTML 파일로 실행 가능해야 함
- 시뮬레이션/계산 기반의 인터랙티브 데모가 핵심
- 요구사항이 명확하고 스코프가 잘 정의됨

## 절차

1. **요구사항 확정** (30-60분)
   - 데모 입력-처리-출력 흐름을 한 문장으로 정의
   - 성공 기준을 명시적으로 기록 (e.g., "출력 지표 3가지 표시")
   - 의존성 제약사항 명확히 함 (사용 가능한 라이브러리, CDN, 등)

2. **계획 수립** (CFA 포함, 30-45분)
   - superpowers:writing-plans 스킬로 구조화된 계획 생성
   - 파일 개수 결정 (보통 1-4개)
   - 태스크 분해 (8-12개 명확한 단계)
   - `docs/superpowers/plans/<날짜>-<프로젝트>.md` 형식으로 저장
   - 계획에 상수·알고리즘·UI 레이아웃 스케치 포함

3. **개발** (1-2일)
   - superpowers:executing-plans 스킬로 계획 추적
   - 각 파일을 한 번에 완성 (반복 수정 최소화)
   - 알고리즘/상수는 하드코딩 후 주석으로 조정 지점 표시
   - 자체 검증 코드(assertion, 콘솔 로그) 포함

4. **검증** (30분)
   - 로컬 브라우저에서 데모 실행
   - 입력값 3-5가지로 출력 확인
   - 성공 기준과 비교

## 주의

- **시간 분해**: "2일"은 실제 개발 시간 ~16-18시간. 계획·테스트에 각 2-3시간 이상 할당 금지; 개발에 집중
- **파일 설계**: 단일 HTML 파일 vs 분할(HTML+JS+CSS)은 처음 계획에서 결정. 변경 불가
- **라이브러리 선택**: CDN 의존성도 "설치 없음" 범주. 용량/로딩 속도 고려하고 계획서에 명시
- **상수 검증**: 알고리즘의 입력 상수(가중치, 임계값 등)는 기획 문서에서 확정되지 않으면, 계획서 단계에서 명시적으로 물음. 개발 중 "추측"하지 말 것
- **UI 초안**: 흐름도나 와이어프레임을 계획서에 텍스트·ASCII 그림으로 넣고 승인받을 것. 코드 작성 후 UI 피드백은 스코프 크리프
- **테스트 데이터**: 하드코딩된 테스트 케이스 3-4개를 주석 형태로 코드에 포함. "다음에 테스트하겠다"는 하지 말 것
- **성능 제약**: 수천 개 이상 데이터 포인트나 실시간 갱신이 필요하면 MVP 범주 초과. 계획서에서 캡핑 명시
